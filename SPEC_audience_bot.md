# Спецификация: телеграм-бот рассылки вакансий для аудитории

> Документ описывает текущий контракт и основные решения реализации.
> Репозиторий: `Aysvoch/vacancy-radar`.

## 1. Суть

Существующий конвейер (Хабр + телеграм-каналы → LLM-оценка → Google Sheets → уведомление в один чат Андрея) расширяется на аудиторию: подписчики телеграм-канала могут подключиться к боту и получать ту же ленту вакансий.

**Лента одна на всех.** Персонализации под каждого пользователя нет. В неё входят вакансии продакт-менеджера без опыта, с требуемым опытом `1–3 года` и `3–6 лет`, а также вакансии, где стаж не указан. Роли с требованием `6+ лет` не рассылаются. География — Россия и удалёнка.

Бот: `@vakansiya_podehala_bot` («Новая вакансия подъехала»).
Канал-гейт: `@Private_ether` («Приватный эфир»), публичный, бот назначен админом.

## 2. Архитектура

Две развязанные части, общего кода нет, общаются по HTTP.

**Часть А — Worker.** Cloudflare Workers, JavaScript. Принимает вебхук Телеграма: команды пользователей и события членства в канале. Хранит подписчиков в Cloudflare KV. Отдаёт список подписчиков по защищённому эндпоинту.

**Часть Б — рассылка.** Python на GitHub Actions. После оценки вакансий забирает список активных подписчиков у Worker и рассылает общую ленту. Личные служебные уведомления остаются отдельными.

Почему так: воркер нужен только для входящих сообщений (GitHub Actions cron для этого не годится - умирает между запусками). Рассылка остаётся там, где уже живёт логика оценки. Python Workers отвергнуты - бета на Pyodide.

## 3. Модель данных (KV)

Ключ - `user_id` пользователя Телеграма. Значение - состояние:

- `state`: `active` | `stopped` | `revoked`
- `subscribed_at` - когда подключился
- `last_checked_at` - когда последний раз подтверждали подписку на канал

`sent_ids` в KV не хранится. Дедупликация общей ленты выполняется на стороне Python через глобальный лист Google Sheets `Аудитория` с полями `source_id` и `sent_at`. Это журнал общей ленты, а не персональная история каждого подписчика.

**В KV не хранить** имена, юзернеймы, тексты сообщений. Только `user_id` и служебные поля. Это персональные данные живых людей.

## 4. Состояния и переходы

| Состояние | Как попал | Рассылка идёт | Как выходит |
|---|---|---|---|
| `active` | прошёл `/start`, будучи подписчиком канала | да | - |
| `stopped` | сам отправил `/stop` | нет | `/start` (с повторной проверкой подписки) |
| `revoked` | вышел из канала | нет | вернуться в канал **И** отправить `/start` |

**Принципиально:** возврат в канал НЕ включает рассылку автоматически. Нужен явный `/start`. Разница смыслов: `stopped` - «не хочу», `revoked` - «нельзя».

## 5. Сценарии воркера

### Команды

| Ситуация | Действие | Ответ |
|---|---|---|
| `/start`, подписан на канал, новый | запись в KV, `active` | приветствие (текст 6.1) |
| `/start`, подписан, уже `active` | KV не трогать | «уже подключён» (6.3) |
| `/start`, подписан, был `stopped`/`revoked` | `active` | приветствие (6.1) |
| `/start`, не подписан на канал | в KV НЕ писать | отказ + ссылка (6.2) |
| `/stop` | `stopped`, запись остаётся | (6.4) |
| `/help` | - | (6.5) |
| любой другой текст | - | (6.6) |

Проверка подписки - `getChatMember` по `@Private_ether`. Подписчиком считать статусы `member`, `administrator`, `creator`. Всё остальное (`left`, `kicked`, `restricted` без членства) - не подписчик.

### События членства в канале

Воркер подписывается на тип апдейта `chat_member` (в `setWebhook`, параметр `allowed_updates` - его надо указать явно, по умолчанию этот тип НЕ приходит).

- Вышел из канала → `revoked`, отправить сообщение (6.7)
- Вернулся в канал → **ничего не делать**, ждать `/start`

### Догоняющий контроль

События могут теряться (вебхук лежал, Телеграм не достучался). Поэтому перед рассылкой воркер перепроверяет подписку у тех, у кого `last_checked_at` старше порога (предлагается 7 дней) - не у всех подряд. Не подтвердилась подписка → `revoked` + сообщение (6.7).

## 7. Рассылка

**Расписание.** Основной слот 06:17 Мск, страховочный 11:17 Мск. Страховочный берёт только вакансии, которых ещё нет в глобальном журнале `Аудитория`, — это защита от пропусков крона GitHub, а не обязательная вторая рассылка. Для пользователя обычно выглядит как «раз в сутки».

**Порог показа.** Как сейчас: в таблицу пишется от 3, в рассылку идёт от 5.

**Пустой прогон - не слать ничего.** Ни аудитории, ни «пока тишина». (Личное «Пу-пу-пуу» Андрею - на его усмотрение, к аудитории не относится.)

**Обработка ошибок при отправке:**

| Ошибка | Смысл | Реакция |
|---|---|---|
| 403 | заблокировал бота / удалил аккаунт | удалить из KV насовсем |
| 400 chat not found | то же | удалить из KV |
| 429 | превышен лимит | ждать ровно `retry_after` из ответа, потом повтор |
| прочие | сеть, 5xx | ретрай с backoff, при исчерпании - пропустить пользователя |

Каждая отправка изолирована: провал одного пользователя не останавливает очередь остальных. Если хотя бы у одного получателя произошёл временный сбой, пачка не подтверждается в глобальном журнале и будет повторена на следующем прогоне. Из-за глобального, а не персонального журнала уже получившие её пользователи могут увидеть повтор — это текущее известное ограничение.

**Лимит Телеграма** ~30 сообщений/сек разным получателям. Между отправками используется небольшая пауза, чтобы сохранить запас при росте аудитории.

**Длина сообщения** - лимит 4096 символов. При кэпе в 10 вакансий реально упереться: резать или разбивать.

## 8. Безопасность

Обязательное, не опции.

- **`secret_token` в `setWebhook`.** URL воркера публичен - без токена кто угодно шлёт поддельные апдейты. Телеграм передаёт токен заголовком `X-Telegram-Bot-Api-Secret-Token`, воркер отвергает всё без совпадения. Сравнение константное по времени.
- **Эндпоинт списка подписчиков** - отдельный секрет в заголовке, константное сравнение, ограничение частоты. Без этого публичный URL = слив базы пользователей.
- **Воркер всегда отвечает Телеграму 200**, даже когда внутри упал. Иначе Телеграм будет бесконечно повторять апдейт. Ошибку - в лог и в алерт, наружу 200.
- **Дедуп апдейтов по `update_id`** - защита от повторной обработки при ретраях Телеграма.
- **Антифлуд на `/start`** - лимит вызовов на `user_id`, иначе один человек накрутит расход `getChatMember`.
- **Валидация входа** - не доверять структуре апдейта, проверять наличие полей до обращения к ним.
- **Секреты только через `wrangler secret`.** НЕ в `wrangler.toml` (уходит в git). Локально - `.dev.vars`, обязательно в `.gitignore`.
- **Токен бота живёт в двух местах** - секрет воркера и GitHub Secrets. При ротации менять оба, иначе половина системы отвалится молча.
- **Логи** - без `user_id` и содержимого сообщений.
- **Алерты** - только на захардкоженный chat_id владельца.

Права бота в канале - минимальные. Для `getChatMember` достаточно статуса админа, конкретные права не нужны.

## 9. Алерты владельцу

Обе части (воркер и Python) шлют Андрею в личку при нештатной ситуации.

**Поводы:** рассылка упала целиком, воркер не достучался до Телеграма, KV недоступен, GitHub Actions не отработал, за сутки не осталось активных подписчиков.

**Ограничения (иначе алерты сами станут проблемой):**
- Троттлинг: одинаковая ошибка не чаще раза в час. При массовом сбое иначе прилетит 48 одинаковых сообщений.
- Отправка алерта не ретраится бесконечно: если сломан сам Телеграм, попытка сообщить об этом через Телеграм зациклится. Одна попытка, дальше - только в лог.

## 10. Открытые хвосты (не блокируют старт)

- Счётчик подписчиков - иначе не видно, растёт аудитория или отваливается.
- Ручная рассылка объявления всем подписчикам (когда-нибудь понадобится: «бот переезжает»).
- Существующий долг проекта: Хабр собирает мало (2-4 поста), проверить парсер.
